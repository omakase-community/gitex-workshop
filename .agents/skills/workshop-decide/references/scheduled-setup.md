# Finish setup through Scheduled

Use when the participant wants repeated work but direct scheduling is unavailable or blocked. This is a guided completion path, not an error-message handoff. Preserve their goal and result.

## Prepare a task that can stand on its own

Carry forward the approved sources, account label, selection criteria, time window, output language, timezone and action boundaries. Resolve only missing choices; keep credentials and unnecessary private content out of the prompt. A standalone run cannot rely on "do what we just did" or an inaccessible previous chat.

Provide a readable task name, schedule settings and one ready-to-paste prompt tailored to the completed workflow. Keep schedule fields separate from the job method. If a skill is needed, name it and select the workshop project that contains it. Include the method in the prompt when it can be concise and self-contained. Use current data each run; preserve a frozen sample clock only for an explicitly requested fictional demonstration.

## Guide the actual next action

Lead positively: "We can finish setting this up from Scheduled. Here's the task text; I'll guide you through it. It becomes active after you save and enable it."

For the desktop app:

1. Ask the participant to open **Scheduled** in the left sidebar and start creating a task. Use the labels shown in their version; do not invent an exact button or deep link.
2. Select the intended project. If the job uses the workshop skills or local files, choose this extracted workshop folder rather than a different project. Explain that standalone runs start with the saved prompt, not all this conversation's context.
3. Paste the prepared prompt. Set the agreed frequency, local time and timezone. Choose the available execution environment appropriate to those sources. Local/project-scoped runs need their files accessible and the computer and app running.
4. Have the participant save/enable the task and inspect its active state and next-run time. Ask what the task card shows when you cannot verify it through tools. Report user-confirmed status as user-confirmed, not tool-verified.
5. Offer a first-run check through the available run control, or inspect the first scheduled result. Confirm that the new run can access the intended sources and that its result matches the agreed scope. Show where the task can be paused.

Present the short route, then help with the next unresolved step; do not turn setup into an intake form or end immediately after supplying the prompt. If the participant wants to stop, retain the prepared prompt and accurately state that setup is unfinished.

## When the expected controls are absent

Ask which app/surface they are using and what options they see. A settings screenshot may help locate controls, but request no private mailbox content. CLI/IDE sessions do not provide the Scheduled management page; guide them to the supported desktop or web interface. When moving to the web, upload or otherwise provide required context through an approved accessible source; a web task cannot read an arbitrary local workshop folder.

If Scheduled is unavailable for their account/workspace too, explain that specific limitation and leave a usable manual-run prompt. Do not imply enabling macOS permissions creates a missing scheduling capability, and do not promise a new chat will fix it. Keep the completed work useful while the account/app availability is checked.

Use [recurrence](recurrence.md) for approval, duplicate avoidance, source scope and notification rules. Keep “prepared,” “saved/active,” and “first run verified” distinct.
