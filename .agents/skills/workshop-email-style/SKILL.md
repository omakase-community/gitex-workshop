# Write Emails in My Style

Read [common behavior](../workshop-decide/references/common.md) and [connection guidance](../workshop-decide/references/connections.md) before the first response. This branch is a conversation, not a mandatory sequence of style analysis, reply drafting, and sending.

## Start with the user's intention

Use what they have already told you. For a request such as "Write an email in my style," lead with connecting their email, not requesting examples to paste: "Let's connect your email so I can learn from messages you've actually sent. Do you use Gmail / Google Workspace or Outlook / Hotmail?" Adapt the wording and language; skip the provider question when already answered. If connected, move to the relevant correspondence scope. If the user already chose samples, supplied the messages they want to use, or declined access, use that choice without pushing a connection.

Follow connection guidance to discover and present the actual setup route. Identify the account and agree on relevant customers, topics, folders, or dates before reading. If the goal needs clarification, ask one useful question about what they want to explore; offer possibilities only when helpful. Source readiness means a usable connection and agreed reading scope, or a consciously selected alternative, not merely that a setup card appeared.

For sample mode, read the [Kivo context](../workshop-decide/assets/kivo-company.txt), then load only the input needed: [sent examples](assets/sent-emails.txt) for voice, [customer thread](assets/email-thread.txt) for conversation context, or both for a styled reply. Explain the participant is acting as Alex Morgan, a Kivo consultant. These are supplied fictional messages, not live inbox findings.

**Ready to explore:** the user's immediate question and input scope are known, and source readiness above is established. Pasted inputs and fictional examples are valid when the participant chooses them; they are not the default shortcut around the connection offer.

## Explore and write together

For voice learning, ask which correspondence represents the intended style. If the user has no preference, propose 5–10 human-written sent messages from the last 30 days; this is a starting option, not a fixed requirement. Learn from the sender's own text, separating quoted replies, forwarded material, signatures, and automated templates. Acknowledge limited or mixed evidence instead of calling a small sample their universal voice. Present a short, tentative style description only when it helps the requested task.

For an existing conversation, read its chronology and latest state before suggesting a reply. For new outreach, establish the recipient and purpose through conversation; completing ICP research is not a prerequisite. Draft in the recipient/conversation language unless the user chooses otherwise. Keep unsupported promises, prices, dates, and attachments out of the draft; ask about material gaps.

Support detours such as “What did this customer ask?”, “Find the email where I promised that”, or “Which of my follow-ups sounds most like me?” Follow the user's new question, retain the return point under common behavior, and avoid re-asking resolved setup questions.

**First useful result:** the chosen question is answered with traceable email evidence, or a usable draft addresses the chosen purpose and distinguishes any unresolved facts. It is not necessary to force both outcomes, a revision, or a send test.

## Continue by choice

Show the result in chat. A neutral "What do you think?" can invite feedback when appropriate; revising, sending, and continuing are optional. Do not assume the draft fails to sound like them. Follow shared behavior for exploration and the menu. Read [delivery](../workshop-decide/references/delivery.md) for an export or approved style profile, and [recurrence](../workshop-decide/references/recurrence.md) for repeated work.

A test-to-self is optional. If requested, use the self-send procedure in [connections](../workshop-decide/references/connections.md), with a distinct test subject and the participant's real own address. A received-message reply can be prepared for review; it is a separate message, not an automatic reply loop. With unavailable sending, retain the draft.
