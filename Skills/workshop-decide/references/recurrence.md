# Turn a useful run into repeated work

## Offer once, then follow the participant

After the first successful day/week brief, offer scheduling even if the participant has not asked yet. Before wording that offer, check the available scheduling tools and their instructions without creating anything. When direct setup is supported, ask naturally: "Would you like me to set this up to run every morning at 10?" Otherwise offer: "Would you like to make this a daily brief? I can prepare the task and guide you through Scheduled." The time is a suggestion, not a configured schedule. Finish an explicit follow-up question before making the offer, and honor an earlier request or refusal without asking again.

For a sample-data brief, explain that the run used fictional inputs and offer to adapt the daily job to their connected work. Do not silently schedule the frozen sample inbox as a real daily assistant. An explicitly requested recurring demonstration may use sample data, but its name, prompt, and reported status must say it is a demonstration.

Other genuinely repeatable workflows may use this procedure when requested or relevant after a useful result. A one-off meeting analysis does not become a surveillance or recording job automatically.

## Configure a real scheduled task only after approval

1. Establish the outcome, approved source/account scope, frequency, local time, and timezone. Reuse what the participant already supplied. Clarify whether "every morning" includes weekends when needed.
2. Verify that the selected host exposes a supported scheduling capability. Discover/read its tool instructions before calling it; use the app's actual scheduling operation rather than writing a directive into chat or editing scheduling configuration by hand. Prefer a task attached to the current conversation for continuation, unless the participant requests a standalone run. Inspect existing matching tasks before creating a duplicate.
3. Verify that the run can access its required context and tools. Local files must remain accessible to its runtime. Explain the host's relevant availability requirements; local scheduled work may need the computer on and the app running. Do not promise cloud execution for a local-only setup.
4. Present or clearly describe the bounded job, then create it when authorized. Reading and preparing a brief/draft are the default operation. Sending mail, deleting messages, or changing CRM records requires its own specific authorization; an approved daily brief does not include these actions.
5. Use the tool result to report what happened: task name, confirmed state, time/timezone, and how to find or pause it. An offer, prepared prompt, suggested creation, or paused task is not an active schedule. If the creation outcome is uncertain, inspect it before retrying.

If the scheduling tool is missing or direct setup is blocked, move to [guided Scheduled setup](scheduled-setup.md). Lead with how to finish the setup, give the ready-to-paste task and guide the next actual user action. Keep status accurate: prepared is not active. A missing tool is not solved by granting blanket computer access; do not change security settings or retry a prohibited computer-control route. If an attempted creation may have succeeded, check for the task before guiding another creation.

## Repeat the method, not stale results

The saved task should specify the participant's goal and selection criteria, not a copy of today's conclusions. Resolve dates relative to each run in the agreed timezone. Retrieve the selected current sources, read newer replies before reviving older requests, distinguish completed/blocked/open items, and link evidence. Keep observations separate from suggested actions. Avoid including raw private messages in the scheduled prompt when source references and a short approved profile suffice.

State the notification behavior agreed for this job. Follow the scheduler's supported notification settings and instructions; do not insert a conflicting policy into its prompt. A requested daily briefing may deliver a daily result. A monitor should not announce unchanged state unless the participant asked for such updates.

## Reusable job brief

Use this as structure, not a mandatory form:

    Purpose: Prepare my day/week work brief.
    Sources: [approved accounts, relevant people/projects, optional calendar].
    Scope: [selection rule and rolling time window].
    Schedule: [frequency, local time, timezone].
    Each run: Re-check current sources; identify commitments, changes,
    unanswered items and upcoming work; propose priorities with evidence;
    prepare only the drafts/actions I have authorized.
    Boundaries: Report missing access. Do not claim complete calendar coverage
    from email alone. Do not send, delete, or change external records unless
    separately authorized. Keep fictional examples out of real-work results.
